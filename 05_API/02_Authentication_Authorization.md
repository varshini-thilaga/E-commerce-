# SALESTORM - Authentication & Authorization

*Note: This document outlines the proposed security architecture for the STORMSHIELD platform.*

## 1. Authentication
Authentication proves the identity of the client. The proposed system utilizes token-based authentication via JSON Web Tokens (JWT).
- Clients include an `Authorization: Bearer <access-token>` header in API requests.
- The system does not create real user credentials in the core application; it relies on an Identity Provider (IdP) to issue tokens.

## 2. Authorization
Authorization determines whether the authenticated identity has permission to perform the requested operation on the specified resource.

## 3. Roles
The system defines the following conceptual roles:
- **CUSTOMER**: A standard authenticated user participating in the flash sale.
- **ADMIN**: A privileged user capable of configuring sales and viewing system-wide analytics.
- **INTERNAL_SERVICE**: A machine-to-machine identity used for inter-service communication.

### Example Role Capabilities
**Customer:**
- View products
- Manage own cart
- Create reservation
- Checkout
- View own orders

**Admin:**
- Manage products/sales/inventory configuration where applicable

**Internal Services:**
- Service-to-service operations according to explicit permissions (e.g., Payment Service notifying Order Service).

## 4. API Gateway Responsibilities
The API Gateway acts as the first line of defense:
- Validates the cryptographic signature of the Bearer token.
- Rejects expired or malformed tokens before they reach backend services.
- Extracts identity claims (e.g., `customerId`, `roles`) and injects them into downstream headers.

## 5. Service-Level Authorization
Individual microservices perform granular authorization checks. For example, the Order Service verifies that the `customerId` in the token matches the owner of the requested `orderId`.

## 6. HTTPS/TLS
All communication between external clients and the API Gateway MUST be encrypted using TLS 1.3 to prevent man-in-the-middle (MITM) attacks and protect Bearer tokens in transit.

## 7. Input Validation
All API inputs are strictly validated against defined schemas to prevent injection attacks (e.g., SQLi, XSS) and logical errors (e.g., negative reservation quantities).

## 8. Request Size Limits
The Gateway enforces payload size limits (e.g., max 100KB per JSON payload) to mitigate buffer overflow and Denial of Service (DoS) attacks.

## 9. Rate Limiting
In addition to flash-sale admission control, standard IP-based and user-based rate limiting is applied to prevent abuse and brute-force attacks on public endpoints.

## 10. Audit Logging
All state-changing operations (POST, PUT, DELETE) and critical administrative actions are logged with correlation IDs, user IDs, and timestamps for security auditing and forensic analysis.

## 11. Secrets Handling
Database credentials, private keys, and API tokens are never hardcoded or exposed in the codebase. They are injected at runtime via secure environment variables or a secrets manager (e.g., HashiCorp Vault).

## 12. Sensitive Payment Information
The platform adheres to PCI-DSS principles. **Raw payment credentials (e.g., credit card numbers, CVVs) are NEVER processed, transmitted, or stored by the STORMSHIELD APIs.** Instead, clients exchange secure tokens generated by third-party payment gateways (e.g., Stripe, Adyen), which are then passed to our Payment API via the `paymentMethodReference` field.
